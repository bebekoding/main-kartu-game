# Administrator access

Implemented 27 October 2026. Replaces the reusable RTDB hash challenge (audit A03).

## Authority

Privileged operations require all of the following in database rules:

- Firebase Authentication password sign-in.
- The exact UID stored in the owner-managed `config/adminUid`.
- The reserved administrator account's server-issued email claim.
- `auth_time >= config/adminAuthAfter`, measured in Unix seconds. A refreshed ID
  token with a newer `iat` does not count as a new sign-in.

The UID is verified against the existing reserved account through the official
Firebase Authentication administrator lookup API. No password, password hash or
list of all accounts is requested. The lookup requests only UID, email, provider
and disabled status. A writable profile is never used to select the administrator.

Browser clients, including the administrator, cannot change either configuration
field. Administrator provisioning and revocation require project-owner tooling.
Changing the UID or advancing the authentication cutoff revokes privileged writes
for the previous identity/sessions. Ordinary room hosts retain their normal rights.

`adminSessions` has no read or write permission and is never checked for authority.
Old stored sessions/hash configuration may remain as inert data; knowing a matching
hash cannot mint a role. The browser no longer calculates, submits or compares hashes.

## Client behavior

- Login and refresh verify access before showing the admin panel.
- No localStorage name, profile field or UI function call grants administrator access.
- Permission loss or an Auth UID change clears cached authorization, account lists
  and refresh timers, and exits administrator spectator mode.
- Async permission/list results are tied to the identity that requested them.
- The administrator uses the existing Firebase Auth password-change modal through
  **Ganti Password**. No second RTDB hash needs updating after a password change.
- Existing administrator sessions must sign in again after the initial cutoff.
  Ordinary player sessions are unaffected by this cutoff.

Never put administrator passwords, hashes, tokens or actual UID provisioning files
in source control or Hosting. Older Git revisions must be treated as disclosed;
this change does not rewrite Git history or establish whether an old password is
still in use. Password rotation is completed by the account owner in the app.

## Verification

`npm test` runs 38 Node tests, including 12 administrator tests using actual app
functions. `npm run test:rules` runs 62 local emulator tests, including 17 cases for
administrator UID binding, hash replay, old-session cutoff, spoofed profiles,
anonymous providers and immediate denial after configuration changes. No test
signs in to a production account or changes a production user's password.

Rules are generated by `node scripts/build-room-rules.cjs`.

Official reference: [Firebase Authentication account lookup](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/lookup).
